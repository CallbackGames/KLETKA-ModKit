Atlas Authoring Guide

Choose the gameplay task, configure its owner data, then connect it through the host's Game Feature actions or components. The same catalogue drives the internal editor and the selected ModKit surface. Use Tools → Atlas: Authoring Guide to return here.

Creation and validation do not prove gameplay acceptance. Each route below ends with checks to run in a compatible game host. Infrastructure areas are integration contracts, not extra assets that every mod must create.

  2. Assign the policies to the NPC configuration provided by the host AtlasAI composition. This plugin owns reusable decisions; the host owns actor, movement and combat wiring.
  3. Check visible/occluded targets, forgotten targets and failed search outcomes in the NPC diagnostics.

AtlasGameplayActorsFramework

Компонентные акторы и точки размещения объектов мира

  1. Start from the component-oriented actor/pawn/controller contracts. Add only the capabilities used by this game.
  2. Let the host GameMode drive spawning; use the spawning manager for start selection and restart callbacks.
  3. Check missing required components before gameplay, spawn/restart, component registration and teardown.
  4. Place an Atlas Actor Placement and configure its default actor, semantic tags and allowed operations. The editor preview shows the base implementation only; keep the generated placement identity when editing a released point.
  5. A mod contributes Add World Actor Rules in its Game Feature: target a tag query or an exact published point, choose Add/Replace/Remove and priority. Equal-priority main replacements are rejected. Existing placed actors are extended with components; arbitrary live actor replacement is not supported.
  6. The game host initializes placements before scene readiness and supplies a stable scene-instance identity. In KLETKA the floor manager composes this with the world save; calling the raw placement API alone does not provide persistence.
  7. Test initial spawn, conflict rejection, destruction, reload and late join. Saved choices retain the exact actor class and never rerun the current rules. Required scene actors must be replicated and always relevant.

AtlasStatisticsSystem

Statistics/Telemetry schemas, Accolade definitions/presets

  1. Create a Statistics Schema with typed keys/defaults and optional bounds. Create accolade definitions/presets for scored results.
  2. Add Accolade Content on the mod Game Feature targets a stable preset ID. Add supplies a new definition; Replace/Remove addresses the original accolade ID. KLETKA player/team result presets are AtlasStatisticsAccoladePreset:DASAP_Player_MatchResult and AtlasStatisticsAccoladePreset:DASAP_Team_MatchResult.
  3. Read effective accolades with Preset.GetAccolades or the registry ResolvePreset. Directly reading Preset.Accolades returns only the authored base. Equal-priority edits to the same target report a conflict; deactivate the mod to restore the prior composition.
  4. Register the schema through the owner contribution and attach a Statistics component to the correct authoritative actor. Report confirmed gameplay facts; telemetry is a separate explicit adapter.
  5. Record a known event and inspect the value, scope/reset behavior and save version. Retry the gameplay action and check it is not counted twice.

AtlasLuaFramework

Lua Script и компонент Lua Behavior

  1. Create a Lua Script asset and assign it to Lua Behavior on an authored actor or a Game Feature component. Source is cooked inside the asset and covered by the mod artifact hash; no loose script files or DLL loading are required.
  2. The Lua Behavior recipe creates an editable door from engine geometry. TriggerScript reads Door State into a copied Variant Store, invokes Lua API 2, filters its signal channel and uses Set Door Opened. Both live and restored states update the same panel pose; BeginPlay only projects current state.
  3. Call Run Lua Event explicitly from the owning Blueprint and handle On Signal through existing public gameplay APIs. Gameplay events run on authority by default; Presentation Only is reserved for local visual/audio behavior.
  4. For owner context, explicitly select Lua API 2 and call Run Lua Event with Context using an Atlas Variant Store. The fifth argument is a copied table keyed by gameplay tags. Bind a public floor, phase or device event, read current state immediately, then send updated snapshots. Keep and remove observer handles at teardown. API 1 retains exactly four arguments.
  5. Filter each On Signal channel and call only the intended public owner command. Check its acceptance result. Context mutation never changes the original store; Lua cannot discover or mutate arbitrary UObjects. A local signal is neither an RPC nor a successful transaction.
  6. Author only the documented event/state/signal API. There is no arbitrary UObject reflection, filesystem or network capability. Instruction, memory, state and output budgets reject invalid events without publishing partial state or signals.
  7. For saved script state, select World Save Group from the host catalogue or a loaded mod world fragment. The Lua Behavior recipe selects the sole available group automatically and adds Atlas Savable; unknown groups are rejected. State Json is collected as a SaveGame component field; disk writes remain explicit. Test save/load, event errors, budgets and component teardown.
  8. Validate, cook and run the mod in the target game with the optional Lua owner enabled. In-editor creation and native automation do not establish packaged multiplayer acceptance.
