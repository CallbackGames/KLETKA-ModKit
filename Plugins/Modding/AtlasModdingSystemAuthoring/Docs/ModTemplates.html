Authoring Guide

Providing Mod Wizard templates

Enabled plugins, including Game Feature plugins, can supply their own categorized starters through their plugin descriptor. They do not need a dependency on the Wizard module. Native editor integrations can also register templates through FAMSModAuthoringProjectTemplates.

Choose a supplied starter

The catalogue for this distribution lists the templates and assets declared by its enabled plugins. Two examples follow.

Open Tools → Atlas: Mod Wizard, select the category and template, inspect its preview, and create a new Game Feature mod. Review the generated assets and next steps before testing, cooking and publishing.

Stable template IDCategory and labelNext work
AtlasInventory.ItemRecipeItems & crafting → Item and recipeConfigure visuals, quantities and an authorized crafting interaction. The starter supplies ingredient, item, recipe, content registration, station and pickup assets.
ElevatorCore.FloorBiomeFloors & biomes → Floor and biomeExtend the initially immediate quest in Quest Flow; design and test the floor. The starter supplies a layout actor, map, quest, floor, bundle, biome and content registration.

Creating a starter does not certify gameplay, save compatibility, multiplayer compatibility or successful publication. Run those checks in a matching game build.

Test a template in the game

In Content, Cook & Publish → PIE gameplay checks, use a standalone or listen-server game with the feature active. The checks read actual gameplay components. To verify what a remote player sees, repeat the action on a joining client.

To preview a hit on a joining player, choose the enemy archetype and a multiplayer test map, then open Play → Remote Player. Enter a game culture such as ru and choose whether to preview with a gamepad. Click Test Enemy on Client. The result folder contains result.json and, with Capture Client Viewport enabled, client-hit.png showing the client’s screen at impact.

  • Crafting. Pick up one starter ingredient, then choose Measure crafting exchange. Use your station once and measure again. The default exchange is one fewer ingredient and one additional product in the player's inventory. Connect your station to an authorized interaction if the counts stay unchanged. Avoid other inventory changes between the two observations.
  • Interaction. Choose Trace interaction failures, attempt a denied action and read the reason on the local player's screen. Disable the feature and repeat the action. Verify its option disappeared and its effect cannot be triggered.
  • Quests. Finish a quest from the selected feature and acknowledge its reward. Capture quest receipts, save and reload, then revisit the same reward trigger. Compare the receipts; each previously rewarded instance should retain its transaction IDs and lifecycle. Compare the inventory or currency balance too if your reward grants either.
  • Weapons and vehicles. Give a sturdy practice target a unique actor tag and enter it in Play / Checks → Damage Target Tag. Measure before and after one baseline shot, install the modifying part and repeat, then remove it and repeat. Use the same weapon, distance and hit zone throughout. The target must survive all three shots. The third health delta should return to the first.
  • Settings. Set Profile Setting Id to the catalog ID of the setting under test. Change its value in the settings screen, apply it, and capture it. Restart PIE, select the same user, and compare. This compares the value and its resolved storage layer on this editor platform. Test the packaged build on each intended device separately.
  • Loot and shops. Activate the contributing features and run Atlas.Loot.Composition PoolId in the editor console for a global pool. For a specific shop, open its assortment and click Preview Effective Stock. The Output Log shows composition order, conflicts, entry source, weight and 64 repeatable catalog draws. The shop preview includes its base stock and matching targeted contributions.

Review a release

Choose Release Summary before cooking or uploading. It shows declared requirements and conflicts, network rules, and a separate status for each target artifact. After cooking, it shows the base and whether dependency fingerprints allow a different base. An archive built for Windows also requires a separate compatibility test on Steam Deck under Proton. Target native Linux independently with the CLI's --platform Linux and its Linux cooking base.

Install the isolated test copy, launch it and select Record Pass or Record Failure after playing. The confirmation window and export bundle carry the author's verdict for this cook. Store download, save reload, online join and on-device testing require their own checks.

Register a template provider

Add this field to the provider's .uplugin. Paths are relative to that plugin. Replace the example owner, identity and paths with your actual values.

"AtlasModTemplates": {
  "SchemaVersion": 1,
  "Templates": [{
    "Id": "YourOwner.YourTemplate",
    "Category": "Your content category",
    "Label": "Your starter",
    "Description": "What is created and what the author must configure next.",
    "Recipe": "Docs/Examples/CreateYourExample.py",
    "RequiredPlugins": ["YourOwner"],
    "AssetPaths": ["Example/DA_YourDefinition"],
    "NextSteps": [
      "Edit the definition.",
      "Test the contribution before Cook & Publish."
    ],
    "SortOrder": 100
  }]
}

SortOrder is optional and defaults to 100. Required string arrays must contain at least one entry. A provider can declare at most 16 templates and each string array at most 32 entries. The recipe must be an existing Python file inside its provider plugin; asset paths must be valid package paths relative to the generated mod root.

Implement the owner recipe

The Python file must export populate_template(plugin_name, content_id). The Wizard calls it after creating and mounting an empty Game Feature. The parameters are the generated plugin name and canonical content identity.

  1. Reject occupied destination packages and a feature already containing actions before writing anything.
  2. Create and save new content only under the generated feature. Preserve the user's open map, unsaved changes and selection.
  3. Wire the canonical owner's Game Feature actions to register the new content. Plugin dependencies alone do not register gameplay content.
  4. Return a dictionary with an assets array containing saved object paths, and an optional map value containing a saved map package path.
{
  "assets": ["/MyMod/Example/DA_YourDefinition.DA_YourDefinition"],
  "map": "/MyMod/Example/L_YourMap"
}

Omit map when no map is created. The Wizard verifies that reported outputs are saved inside the new mod. It records them in the creation result and keeps a recipe completion receipt under Saved/ModTemplates.

Use the installed owner examples as working implementations: AtlasInventorySystem/Docs/Examples/CreateInventoryModExample.py and ElevatorCore/Docs/Examples/CreateFloorModExample.py. Their populate_template entry points populate an already created feature; their standalone create_example helpers create that feature first.

Availability, conflicts and failure

Descriptor changes refresh on the next template-registry lookup. Disabling a provider removes its descriptor registrations. Templates are grouped by category and ordered by sort order, label and stable identity. IDs must be unique across providers: a conflicting identity is unavailable until the conflict is removed. Empty and reserved None identities are invalid.

PythonScriptPlugin must be enabled and initialized; finish Play In Editor before creating starter content. If generation fails, the Wizard retains the partial plugin and its incomplete-creation guard. Read the creation report and recipe error before retrying. Do not remove the guard merely to publish incomplete content.

Recipes are trusted editor tooling and execute with editor access. They are not sandboxed player mods. Listing templates does not execute a recipe, and activating a gameplay Game Feature in the player game does not execute its authoring recipe.

Native editor providers

Register an FAMSModAuthoringProjectTemplate with a stable template ID and owner, and unregister that owner's entries on shutdown. Re-registering a key by the same owner updates it. Cross-owner conflicts stay unavailable, independently of registration order. Use the approved headers from the NativeSdk distribution; private implementation helpers are not public runtime APIs.
