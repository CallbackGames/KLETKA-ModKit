Save content compatibility

The save manifest and the content registry answer different questions. A package being installed does not prove that it can run on the current game/platform, read a saved payload, or reproduce a saved world's composition. Remote download availability and DLC ownership are separate provider checks.

Authoring contract

  • Keep the canonical content ID and Mods.<ContentId>.<Fragment> IDs stable. A display-name change is not a migration, and an ID rename is not automatically an alias.
  • bRequiredForSave is a persisted requirement. Making a later release optional cannot remove the requirement from an existing save.
  • Required fragments promote their transitive dependencies to required state. An optional fragment used by required gameplay is therefore critical.
  • Typed fragment schema versions and explicit migrations own payload compatibility. A semver increase or an unchanged version string proves nothing about saved data. The active descriptor's supported data-schema interval is checked before migration callbacks; each payload still passes its own schema validation and migration transaction.
  • Use exact compatibility hashes where content identity is required. Cross-platform compatibility hashes describe semantically equivalent content; platform archive hashes still protect downloaded bytes. Do not reuse a compatibility hash for changed gameplay content.
  • Independent optional data can remain opaque when its contributor is absent or inactive. The ordinary save pipeline retains those bytes for a later return of the mod. An active incompatible decoder is blocked even if its data is optional: it must not consume bytes it cannot understand.
  • A new required fragment needs an explicit supported initialization/migration path for older saves. A dependency cycle or missing critical fragment is an error, not permission to drop progress.

The framework cannot infer whether arbitrary user-authored payload bytes contain a meaningful biome, actor, quest or item reference. Authors must declare dependencies; product composition conservatively records gameplay packages as critical even when they do not own a save fragment. Automatic semantic recovery of deleted content is not provided.

Inventory and review

Manifest format 6 adds a complete-inventory marker and readable package names. Older saves remain readable but may only list fragment contributors. A nonempty legacy content-profile hash with an incomplete inventory produces an explicit warning; the reader does not invent the missing IDs.

FAtlasSaveCompatibility::Evaluate is provider-neutral, read-only policy. Its per-mod result separates installed/active state, runtime availability, saved and installed versions, criticality, blocking and the cause. UAtlasSaveSubsystem::ReviewSaveSlot exposes it to Blueprint without opening a save, activating features or executing migration callbacks.

Source composition contributes full session requirements through OnCollectContentRequirements. bRequireCurrentContentProfile opts a profile into the product's OnReviewContentRequirements policy. For a run without a supported world migration, RequireSessionProfile requires its original blocking composition. A compatible fragment schema cannot waive that world constraint. Additional gameplay packages, changed runtime contracts or an incompatible game build may therefore block the whole run even when every listed mod is present.

Catalogue cache hits re-evaluate the current content policy. FAtlasSaveOpenOptions::ExpectedRevision binds an explicit player confirmation to the exact reviewed revision. A replacement from cloud storage requires a new review. Confirmation does not replace the existing integrity, migration, concurrency, rollback, world-readiness or session-admission gates.

Download and recovery boundaries

Never equate an installed package with an available download. A provider may require sign-in, deny access to a private release, remove a file, lack the saved version, or lack an approved artifact for this platform. Do not automatically install the latest release in place of the required revision. Keep the original save and give a precise explanation when no compatible artifact is available.

Cancellation and review do not write a save. A successful migration is applied through the canonical transactional opener; subsequent persistence uses the normal verified-generation writer. Do not add a UI action that deletes missing critical payloads merely to bypass a blocker. A future destructive recovery feature would require a separate copy and an explicit, domain-owned migration policy.

External precedents

Checked 2026-10-19:

  • Factorio migration documentation: explicit migrations for old game/mod saves, deterministic order and records of already-applied migrations; prototype deletion can invalidate references.
  • Baldur's Gate 3 cross-play guide: a Mod Verification window identifies installation/update/removal discrepancies; party content must be available on the participants' platforms. Its numerical mod limits are game-specific.
  • mod.io multiplayer documentation: session content delivery is a separate concern from a game's persistence migrations.

These are design precedents, not evidence that a particular KLETKA build or console has passed testing. Verification receipts belong in the product's release report.

## Recovering a saved release

Manifest format 7 adds provider source hints and, when available, an immutable provider file ID for the platform. These fields contain no credentials or expiring CDN links. Keep the original source records when retaining opaque fragments. An older save with no source can use the currently installed manifest's source records; the UI never guesses a remote ID from a display name.

FAtlasModDescriptor::PlatformArtifactHashes additionally records known cooked-package checksums by lowercase platform key. This is an additive tagged save field: an older descriptor reads with an empty map. Product composition obtains these checksums from the active validated content profile, not from a catalog's display name or current download. Preserve the map with opaque mod requirements. A semantic content hash does not replace the platform checksum.

The product recovery adapter first checks recorded sources. If none can supply the saved release, it may search permitted catalogs for the exact canonical content ID. Unknown-store discovery requires the saved version and a valid SHA-256 for the current platform. It accepts one distinct matching store item; duplicate cards for that same item are harmless, while conflicting items, truncated results and other-platform references are refused. The selected provider must then resolve the saved version and hashes before a download is offered. A file ID from one store is never forwarded to another. Legacy saves without a platform checksum retain recorded-source recovery and explain why unknown-store discovery is unavailable.

Catalog discovery is read-only and does not subscribe, download, activate content or rewrite the save. Queries are serialized and bounded; cancellation, account changes and UGC restrictions stop pending work. Changing a saved platform checksum also invalidates the previous review approval.

The save review resolves remote releases separately from local compatibility. A resolved file enables an explicit per-mod download action. Download availability does not enable loading. After installation the canonical manifest/game-build/API checks, version and required content hash are applied again; the save must then pass its ordinary content review and transactional open. A changed save revision, owner or source invalidates download confirmation. Loaded content cannot be replaced in place.

The host supplies recovery through UAtlasSaveSubsystem::OnRecoverContentRequirements; it owns account/UGC permission checks and provider routing. The save framework and its UI do not depend on a storefront implementation. Cancellation releases query resources and prevents stale UI callbacks. A subscription transfer already delegated to a storefront may finish in that storefront's client after the review closes.

mod.io: the current accessible platform release is installed through the official SDK. A narrow SDK extension requests the file-history endpoint for an exact older version/file ID through the SDK transport, including its current account, portal and platform context. No access token is exported to the Atlas layer. The SDK preserves its platform header and requests only live/approved files. A file with platform records must be approved for the requested platform. On desktop, an explicitly empty platform list also supports games using mod.io global-file mode; this never establishes console approval. The extracted manifest must still contain a compatible platform artifact. A usable secure download URL is required and ambiguous version labels are refused. The archive is streamed to a private staging directory, checked against its provider checksum, unpacked with traversal/link/duplicate/size checks and validated before selection. The prior selected release stays selected on failure. The new archive installer is compiled for desktop platforms with the engine's libzip dependency. Private/paid history remains subject to the current account's actual service permissions. Deleted files, unsupported platform builds and inaccessible metadata produce explicit failure reasons, not a substitute latest version. Private current releases continue to use the authenticated SDK path. The bundled project extension is optional: stock SDK builds lacking it report history recovery as unavailable and still support current releases. Console archive installation needs a supported platform build and device validation.

Steam Workshop: current item metadata must identify this game's stable content ID and the required version. ISteamUGC::DownloadItem has no historical revision argument. A mismatching current release is reported as unavailable through that item; a separately published legacy item or a recorded mod.io source can provide an alternative. Publish the content_id and ams_version metadata through the ModKit uploader.

Author guidance: preserve stable IDs, publish distinct release labels and retain approved compatible files. Publish each platform artifact and provider reference intentionally. A shared compatibility hash must describe equivalent gameplay content across platforms; the Windows file ID is not a console file ID. Schema migration remains an explicit author-owned contract. No provider resolver can repair arbitrary deleted world content.

Provider references: mod.io file history, platform filtering, Steam UGC API.
